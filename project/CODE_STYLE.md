# Стиль кода и правила работы BallDecor

Соблюдение этого документа обязательно при выполнении задач проекта. Правила закрепляют замечания и корректировки владельца и дополняют [AGENTS.md](../AGENTS.md). Новые согласованные правила добавляем сюда по мере работы.

## Язык и границы работы

- Общение, документация, комментарии и тексты сайта — на русском языке. Технические идентификаторы сохраняем совместимыми с инструментами. Явное указание владельца о языке конкретного коммита имеет приоритет; для текущего коммита согласован английский.
- Двигаемся отдельными согласованными шагами. Не реализуем остальные этапы дорожной карты автоматически вместе с текущим шагом.
- При заведении задач создаём отдельные папки. Если запрошены пустые README для ворклогов, оставляем их пустыми до последующего указания.
- Трудозатраты записываем только по итоговым показаниям таймеров владельца. Самостоятельно время не считаем.

## Структура моделей GraphQL

- Каждая модель обособлена в `server/schema/types/<Model>/`. Вспомогательная модель также имеет собственный каталог: `OldTemplateValue` не объявляется внутри `OldResource`.
- `index.ts` описывает GraphQL-модель и подключает её резолверы. Не используем его для barrel-реэкспортов.
- `interfaces.ts` содержит TypeScript-контракты модели и строк базы.
- `types.ts` содержит ссылку Pothos на модель и связанные определения типов, когда они нужны.
- `inputs.ts` содержит именованные входные типы GraphQL.
- Каждый корневой резолвер находится в отдельном файле `resolvers/<queryName>.ts`. Не объединяем все запросы в один `queries.ts`.
- Резолверы полей связей также выносим в отдельные файлы: например, `OldResource/resolvers/TVs.ts`.
- Общую логику построения SQL выносим в `helpers/`, чтобы список, подсчёт и получение одного объекта использовали согласованные фильтры.
- Образец организации: `/disks/wd-1000/www/haih/agent/server/schema/types/Post`. Переносим принципы структуры, а не ненужные зависимости или функциональность примера.

## Имена запросов и входные аргументы

- Для списка ресурсов используем `oldResources`, для одного ресурса — `oldResource`, для количества — `oldResourcesCount`.
- Не используем прежние имена `oldResourceList`, `oldResourceGetOne`, `oldResourceCount`.
- `oldResources` принимает необязательный `where: OldResourceWhereInput`. `oldResourcesCount` использует тот же тип фильтра.
- `oldResource` принимает обязательный `where: OldResourceWhereUniqueInput!`. Не размещаем `id`, `uri` и `context_key` непосредственно в аргументах запроса.
- `OldResourceWhereUniqueInput` содержит `id`, `uri` и дополнительный `context_key`. Необходим хотя бы один идентификатор: `id` или `uri`.
- При изменении контракта сразу обновляем все обращения к нему, интеграционные тесты и примеры в документации.

```graphql
query {
  oldResources(where: { parent: 0 }, take: 20, skip: 0) { id uri }
  oldResourcesCount(where: { parent: 0 })
  oldResource(where: { id: 1 }) { id TVs { name value } }
}
```

## Порядок действий в резолвере одного ресурса

1. Сначала создаём Knex query и назначаем его локальной переменной `query`.
2. Затем проверяем наличие `id` **или** `uri`.
3. Если хотя бы одно поле передано, возвращаем query.
4. Если оба отсутствуют, выбрасываем `GraphQLError` с кодом `BAD_USER_INPUT`.

Создание Knex QueryBuilder не выполняет SQL. До проверки обязательного идентификатора нельзя вызывать `await` или `.then()` для query. Пустой `where`, оба поля со значением `null` и один `context_key` должны завершаться ошибкой без обращения к БД. Наличие проверяем через `null`/`undefined`, а не через truthiness: пустой URI может обозначать главную страницу.

## Чтение старой базы и TV

- Подключение — Knex с `mysql2`, серверная переменная `MYSQL_URL`, клиент в контексте Pothos. Доступы не включаем в Git.
- На текущем этапе читаем существующую MySQL; не добавляем миграции и операции записи без отдельной задачи.
- Поле ресурса называется `TVs`, его элементы имеют тип `OldTemplateValue`.
- TV загружаются отдельным резолвером только при запросе поля. При обычном запросе списка без `TVs` SQL к таблицам TV не выполняется.
- N+1 для этой связи принят владельцем: TV планируется запрашивать у конкретного документа, а не в списках. Не добавляем DataLoader или предварительную загрузку без новой необходимости.
- Текущий контракт возвращает сохранённые значения TV. Вычисление значений по умолчанию и MODX-привязок не входит в этот шаг.

## Проверки и завершение работы

- После изменений запускаем полный `npm run lint` и `npm run types`. Проверки только изменённых файлов не заменяют полный линтер.
- TypeScript-тесты включаем в `tsconfig.json`, чтобы их видели TypeScript и ESLint project service. Действительные глобальные объекты среды описываем в ESLint; не отключаем проверку ради устранения сообщения.
- Для изменений резолверов запускаем `node --import tsx --test tests/old-resources.test.ts` на локальной копии MySQL. Проверяем корректные выборки, ошибки аргументов и отсутствие лишних SQL-запросов.
- Сообщение владельца с командой проверки или указанием ошибки в ходе разработки означает необходимость выполнить проверку и исправить найденное, а не только пересказать ошибку.
- Не объявляем работу проверенной по одной успешной команде. Указываем фактически выполненные проверки и оставшиеся ограничения.
- Коммит и amend выполняем по запросу владельца. Перед ними проверяем состав изменений; секреты и посторонние игнорируемые файлы не добавляем. Запрошенные документы в игнорируемом `project/` добавляем адресно.

## Общие соглашения проекта

- Именованные экспорты, без `export default` и barrel-экспортов. React-компоненты объявляем через `React.FC`.
- Максимальное покрытие TypeScript: типизируем контракты, параметры и результаты; избегаем `any`.
- Стили — colocated `styles.ts` с Linaria `styled`, mobile-first. Не заменяем их отдельными CSS-файлами или CSS Modules.
- Остальные архитектурные требования, границы модулей и правила проверки окружений сохраняются в [AGENTS.md](../AGENTS.md).
