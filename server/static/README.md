# Статическая сборка BallDecor

`npm run build` читает текущую SQLite и генерирует HTML и `.data` для главной,
всех опубликованных концептов и их алиасов. Концепты `hidden` доступны по прямой
ссылке, как и в API; `unpublished` не попадают в сборку. Каталог содержит снимок
публичного списка и выполняет пагинацию без обращения к API. Пользователи,
авторизация и чат продолжают обращаться к API из браузера.

Сборка временно запускает отдельный GraphQL API на свободном loopback-порту.
Dev-сервер для неё не нужен. В проде SSR отсутствует: `server/static` отдаёт
файлы, сохраняет статусы и редиректы по `build/static/pages.json`, а неизвестные
URL возвращают 404. Sitemap также создаётся при сборке.

## Docker-сборка

Процесс сборки и назначение `scripts/build.ts` описаны в
[корневом README](../../README.md#сборка-balldecor).

Перед production-сборкой остановите dev-сервер и все другие процессы,
использующие исходную SQLite. Из корня репозитория выполните:

```sh
docker compose -f docker/compose.yaml -f docker/compose.prod.yaml build app
```

`target: production` выбирает нужные стадии Dockerfile. Обычный `COPY . .`
копирует `server/database/data`, включая возможные WAL-файлы, в сборочную
стадию; затем `npm run build` читает эту копию. Исходная БД должна оставаться
остановленной до завершения сборки. Финальная стадия получает только билд и
runtime-файлы, поэтому SQLite в итоговый образ не попадает. Отдельные снимки,
обёртка `build:docker`, build secrets и дополнительные контексты не нужны.

Картинки из `img src` в контенте не скачиваются сборщиком. В HTML сохраняются
URL; файлы продолжают обслуживаться отдельно из подключённых `uploads` и
`shared`. Vite по-прежнему включает файлы `public` и импортированные кодом
ассеты. Рабочая БД в production нужна API, но не отдаче страниц концептов.

Изменения контента публикуются новой сборкой и заменой образа. HTML, `.data` и
sitemap отдаются с `Cache-Control: no-cache`; при публикации через Varnish
нужно также учитывать действующую конфигурацию кеша и её инвалидирование.
